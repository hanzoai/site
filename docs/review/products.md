# /products/* — James-eye review

Verdict: 7/10
First complaint: "The product is meant to be the hero, and for the first five or six seconds it's an empty box with lines in it. On a slow load the table shows up and then fades away again. Show me the thing working straight away."

Walked 7 Nov 2026 with Playwright on the running dev server. I walked /products/agents and /products/memory fully at 1470×801 and at 375×812 (isMobile, hasTouch), with video. I took frames at 0.3, 0.7, 1, 1.5, 2.5, 4, 6 and 9 s with no input, and a dense 150 ms sample of the first 3.5 s on memory. Then I wheel-scrolled the whole page in 300 px steps (smooth touch scrolling on the phone), hovered table rows, the magnetic ask and the Hanzo OS rows, pressed Replay and Copy (and read the clipboard back), and ran a 70-stop Tab crawl. I also checked reduced motion, JS off and 320 px. /products/models and /products/record were spot-checked the same way for states, the hero, the keyboard and Copy. Non-localhost POSTs were blocked.

Shared chrome, noted and not counted: the "1 Issue" badge is a hydration mismatch in `FooterHTML` (the site footer's `dangerouslySetInnerHTML`), not this page. The 0.004–0.012 layout shifts are in the header's right-hand cluster. The cookie card sits over the console's last row. On phones the header's solid "Try Hanzo" sits beside the hero's solid ask.

Stills: `products/memory-load-ghost.jpg` (0.94 s: the table fading out after it arms), `products/memory-pinned-scrub.jpg` (the pinned console with sentence 03 lighting `/v1/graph/answer`), `products/memory-measured.jpg` (the measured grid with its hole).

## What works
- **The layout is a real Apple launch shape.** The name, its line and the ask sit over a light, page-wide console. At 1470×801 the h1 (y 117–192), the ask (y 144–192) and the whole console (y 220–744) are on the first screen on memory, agents (console to 773) and record.
- **The pinned scene is the best thing in the family.** The console holds under the header while Hanzo's paragraph slides by underneath, a sentence at a time (translateX 0 → −45% on memory, over about 1,900 px of scroll). The sentence in ink lights the operations it names: sentence 03 on memory lights `/v1/graph/answer`, sentence 02 on agents lights `/run` and `/budget`. This is "one thing in, one thing out" and it ties the words to the product.
- **Calm and on palette.** Ink, greys and white only. GET is an outline and POST a fill, told apart by shape and not hue. There is one dark room (the closing band). `taste.py` OK. No eyebrow over a heading.
- **Copy equals display**, measured on all four pages: 545/545, 429/429, 210/210 and 131/131 characters. The button says "Copied".
- **Resilience is solid.** Reduced motion and JS off both show the finished request and table on all four pages (0 hidden blocks, 0 running animations after 3.5 s). There is no horizontal scroll at 320 or 375. All 25–28 tab stops in main show a ring, and none lands under the header.
- **Parity is clean:** agents 60/60 and 21/21 links, memory 59/59 and 19/19, models 54/54 and 18/18, record 53/53 and 20/20. `unique.py` OK.
- **Hover tells you something.** A Hanzo OS row reveals the layer's operation count ("6 API"), and a table row fills under the pointer.

## The 11 answers
1. **Does it sell in 5 s, and move within 1 s?** Partly. The name, line and ask sell at once, and the h1 arrives at 72 px and settles to 52 as you scroll. The object does not sell yet. On desktop, at 0.3 s the console is a grid of empty hairlines. At about 0.8 s, when it arms, the server-rendered rows become visible and then fade out (row opacity 1 → 0.16 → 0 between 0.79 and 1.15 s: a ghost table). The request then types at 110 characters a second: 545 characters on memory is about 5 s. The rows land at about 6.3 s and the walk runs until about 10.5 s. For the first six seconds the hero object on memory is mostly blank. Agents (429 characters) is about 4 s, and record and models are short.
2. **One thing in, one out, or a document?** On desktop, one in and one out through the pinned stage. Then Measured (memory only), Hanzo OS, the docs and the band follow as plain stacked sections. On the phone the stage does not pin (it is stacked, as the rules say). The console is 1,041–1,065 px tall, so the sentence rail arrives more than a full screen after the hero, and the rest reads as a long document.
3. **A real visual object in every section?** The console, the figures and the layer list are all real. The docs block is links only, but that is a quiet coda, which is acceptable. On record and models the request pane is two to four lines in a 470 px pane, so half the hero object is white.
4. **One ask in Hanzo's words, sticky, nothing floating? Scale rhythm?** Yes to the ask: "Try Hanzo" solid in the hero, carried into the header after the hero, and solid again only in the closing band. Nothing of the page's own floats. Scale mostly has rhythm: the h1 settles 72 → 52, sentences are 32, table text 14, figures 64, and the first figure grows ×1.6 at its moment. Section heads sit at 44 against the 26 px rest in JAMES.md. That is tolerable because each is alone on its screen, but it is a deviation the card should own. The growing 37.5 pushes against the top of its card (about 16 px from the edge at its peak), which looks cramped rather than intended.
5. **Does every hover and press answer, with no jumps?** Yes. Rows fill, Replay changes border and fill and presses at .97, the Measured cards and site pills press, and Copy confirms. The magnetic ask read `none` from my pointer probe (I moved just outside its edge), so it is unproven. The one jump is the sentence strip: before `desk` is known, each `li` is 239 px wide (four squeezed columns, "01 The graph 02 A read 03 So a past 04 Each", visible at the fold). At about 0.9 s they snap to 858 px. That re-layout is visible at the bottom of the first screen on memory and models.
6. **Overlaps, font swap, layout shift?** No text overlap at either size (pairwise box check: 0). Page CLS is 0.0017–0.012, all from the header. There are two visual jumps that CLS does not catch: the table fading out on arming, and the strip snapping wide. On the phone, the first strip card's grey (#f5f5f5) runs into Measured's identical grey, so the card loses its bottom edge.
7. **Which reference, and is its motion there?** apple.com product page: the product as hero, one pinned scene with a scrubbed strip, and a persistent ask. That motion is genuinely there on desktop. The Morph from layer rows into the next page's h1 is wired (`data-morph` to `data-morph-target`). I did not film it end to end, because the dev server holds 2–3 s on a fresh render.
8. **Different from its neighbours?** Yes against /oss and /solutions (no black card beside the title). Inside the family, all seven members are the same page with different words. The Sigil contour that is meant to tell them apart is a faint 14%-opacity ring behind the lede that you barely see. A family template allows this, but nothing visual says "Memory" rather than "Record".
9. **All 18 parts covered?** The card exists with 18 headings, all filled. Mostly truthful; see the card check.
10. **Banned tells?** None: no hue, no gradient text, no pill over a heading, no icon boxes, no fade-on-hover buttons. The Hanzo OS count fades in on hover, but that is a revealed detail, not a fading button.
11. **Copy untouched?** Yes. Parity is 0 missing on all four pages checked, and the paragraph is in the HTML whole (`x-sr`), with the strip as its `aria-hidden` picture.

## Card check
`docs/coverage/products.md` exists, has exactly 18 parts and fills every `Done here:` line. Inaccuracies:
- Part 1 and part 6 say the h1 "arrives up to 84". Measured: 72 px (`fam.css` caps `[data-settle]` at `clamp(52px, 4.9vw, 72px)`).
- Part 17 says JS off and reduced motion show the final state. True. But "a CSS failsafe shows them after 3.5 s if arming never happens" leaves out that, with JS on, the finished rows are painted and then faded out when the console arms. That flash is not acknowledged anywhere.
- Part 11 says "no layout shift as rows land: CLS 0.001". True by the metric, but the strip's 239 → 858 px snap at hydration is a visible re-layout the card does not mention.
- Part 6 lists "section heads 44" as if within the rules. JAMES.md rests section headings at 26 px; a deviation like that should be noted as a decision on the card.
- Part 18 still points at `docs/review/products-family.md`. This review (`docs/review/products.md`) replaces it.

## To reach 8
- **Fix the hero object's first six seconds (the main fix).** Arm before first paint, not after hydration. Either put `data-armed` in the server HTML whenever `html.js` is set (CSS-only: the rows start at opacity 0 with no transition), or turn off the row transition while arming, so the table never paints and then fades. Then shorten the empty time. Either start the rows landing while the request is still typing (for example, row *i* lands when the request types the path it names), or type faster for long requests: cap the typing at about 2 s, as MASTER's 6–10 s demo budget is for the whole run. At no moment after 1.5 s should the API table be empty.
- **Stop the strip snapping on hydration.** Give the strip its desktop layout in CSS (`@media (min-width: 901px)` with `width: calc(var(--n) * 100%)`) so the server HTML already has the wide sentences, and let JS add only the `x` transform. Never render the squeezed 239 px columns.
- **Make the phone a composition, not a long stack.** On 375×812 the console is over 1,000 px tall. Cap the table's height with its own scroll (or show the first 3 operations and open the rest), so the sentence rail and the next idea arrive within a screen. Give the strip cards a white fill or a hairline where they meet the grey Measured room. On the Hanzo OS rows, the bare "6" with its label hidden means nothing: keep the mono label, or drop the number on phone.
- **Tidy Measured.** Three figures in a 7/5/5 pattern leave a 7-column hole beside the third card. Use 7/5 then a full-width or centred 12 for an odd last card, or put the CronQuestions text row into that space. Give the growing first figure room (top padding or a smaller grow) so 37.5 never crowds the card edge at its peak.
- **Fill the short consoles.** On record (2 lines) and models (4 lines), the request pane is mostly white at 470 px. Size the pane to the request (shorter console height when the request is short) so the hero object looks full on every member.
- **Correct the card** (84 → 72, note the 44 px section-head decision, note the arming flash once it is fixed, point part 18 at `docs/review/products.md`).
